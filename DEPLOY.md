# Deploying NeighbourAid

Three free services, ~30 minutes, no credit card:

| Piece | Host | Cost |
|---|---|---|
| Backend (FastAPI + WebSockets) | Render — free web service, Singapore | Free |
| Database | MongoDB Atlas M0, Mumbai (`ap-south-1`) | Free |
| Frontend (React SPA) | Cloudflare Pages | Free |
| Keep-alive cron | Cloudflare Workers | Free |

## The constraint behind these choices

`app/services/websocket.py` keeps connected volunteers in a plain in-process
dict. Two consequences shape everything below:

1. **The backend cannot run serverless.** No Vercel/Netlify Functions, no
   Lambda, no Workers — it needs one long-lived process holding open sockets.
2. **The backend cannot run more than one instance.** A second instance holds
   a second, invisible half of the volunteer pool, and an alert broadcast
   reaches only whoever happens to share a box with the reporter. Render's
   free plan cannot autoscale, which makes this safe by construction — but it
   is also the ceiling. Lifting it means moving the manager behind Redis
   pub/sub first.

---

## 1. Database — MongoDB Atlas

1. Create a free **M0** cluster. Pick **Mumbai / `ap-south-1`** — the app is
   India-facing, and every query crosses this link.
2. **Database Access** → add a user, copy the password.
3. **Network Access** → add `0.0.0.0/0`. Render free services have no static
   egress IP, so an allow-list is not an option here. The database user's
   password is the actual access control; make it long and random.
4. Copy the connection string from **Connect → Drivers**:

   ```
   mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/neighbouraid?retryWrites=true&w=majority
   ```

   Keep the `/neighbouraid` path segment. Without it the driver has no default
   database — `app/db/client.py` falls back to that same name, so it works
   either way, but explicit beats implicit in a connection string.

Indexes (including the `2dsphere` geo index the map and radius queries need)
are created on startup, so there is nothing to run by hand.

## 2. Backend — Render

The repo has a [render.yaml](render.yaml) blueprint, so this is mostly clicks.

1. **New → Blueprint**, point it at this repo. Render reads `render.yaml` and
   proposes `neighbouraid-api`.
2. Fill in the two prompted secrets:
   - `MONGO_URL` — the Atlas string from step 1
   - `ANTHROPIC_API_KEY` — optional. Without it, triage falls back to the
     keyword heuristic in `app/services/ai.py` and the app works fine, just
     less accurately on unusual phrasing. With it, roughly $0.008 per alert.
3. `JWT_SECRET` is generated by Render — never paste your own unless you have
   a reason. `ENVIRONMENT=production` is already set, which makes the app
   refuse to boot on the public dev signing key.

Verify:

```bash
curl https://YOUR-APP.onrender.com/health         # {"status":"ok"}
curl https://YOUR-APP.onrender.com/health/ready   # {"status":"ok","database":"ok",...}
```

`/health/ready` is the one that proves Atlas is actually reachable. If it
returns `503 database: unreachable`, the connection string or the Network
Access rule is wrong.

## 3. Keeping it warm

Render spins a free service down after **15 minutes** without an inbound
request, and the cold start back up takes roughly **50 seconds**. For a normal
side project that is a shrug. Here the first request after an idle stretch is
someone pressing SOS — so the app's entire promise is spent waiting for a
container to boot.

[ops/keepalive](ops/keepalive) is a Cloudflare Worker that pings `/health`
every 10 minutes. You are already on Cloudflare for the frontend, so this is a
schedule, not another vendor.

```bash
cd ops/keepalive
npm install
# set BACKEND_URL in wrangler.toml to your Render URL first
npx wrangler deploy
```

Confirm it works without waiting for a tick:

```bash
curl https://neighbouraid-keepalive.YOUR-SUBDOMAIN.workers.dev/ping
# {"ok": true, "status": 200, "ms": 180}
```

An `ms` in the thousands means the ping arrived after the service had already
gone cold — check that the cron is firing (`npx wrangler tail`).

**Why `/health` and not `/health/ready`:** the keep-alive must never be able to
take the service down. `/health` deliberately checks nothing, so a transient
Atlas blip cannot cause the platform to recycle a healthy container. Point
uptime monitoring at `/health/ready` instead — that is the endpoint that
answers "can it serve an alert?"

**Budget:** Render gives 750 free instance-hours/month and a calendar month is
~730, so one always-warm service fits — but only one. A second free service on
the same account pushes you over and both get suspended.

## 4. Frontend — Cloudflare Pages

1. **Workers & Pages → Create → Pages → Connect to Git**.
2. Build settings:
   - Framework preset: **Vite**
   - Root directory: `frontend`
   - Build command: `npm run build`
   - Output directory: `dist`
3. Environment variables (Production **and** Preview):

   ```
   VITE_API_URL = https://YOUR-APP.onrender.com
   VITE_WS_URL  = wss://YOUR-APP.onrender.com
   ```

   `wss://`, not `ws://`. A browser on an https:// page blocks insecure
   WebSockets, and the failure surfaces as a volunteer feed that simply never
   receives anything — no error, no clue.

Two files in `frontend/public/` are already doing work here:
[`_headers`](frontend/public/_headers) applies the CSP and security headers at
the edge, and [`_redirects`](frontend/public/_redirects) rewrites all paths to
`index.html` so a shared link to `/map` or a specific alert loads the app
instead of a 404.

CORS needs nothing: the regex in `app/main.py` already allows `*.pages.dev`.
On a custom domain, set `FRONTEND_ORIGINS=https://your-domain.com` on Render.

## Post-deploy checks

Worth doing in this order — each one fails differently:

1. `GET /health/ready` returns `database: ok` — Atlas is wired up.
2. Register an account on the Pages URL — the API and CORS are wired up.
3. Open the volunteer feed in one tab, post an alert from another browser.
   The alert should appear **without a refresh** — that is the WebSocket, and
   it is the piece most likely to be misconfigured (`wss://` vs `ws://`).
4. Deep-link straight to `/map` in a fresh tab — confirms `_redirects` landed.
5. Switch the language to Tamil and watch the network tab: exactly one small
   `ta-*.js` chunk should load. The other six languages should never be
   fetched.

## Known limits of this setup

- **Single instance only.** See the constraint section above. This is the
  first thing to fix if the app gets real traffic.
- **Cold start after ~15 min of cron failure.** The keep-alive is a mitigation,
  not a guarantee. A paid Render instance ($7/mo) removes the idle timer.
- **512 MB RAM / 0.1 CPU** on Render free. Fine for this workload; triage runs
  on Anthropic's servers, not yours.
- **Singapore, not Mumbai.** Render has no Indian region, so expect ~60-80ms
  of extra latency versus a Mumbai host. Atlas being in Mumbai keeps the
  database round trips off that path — the app-to-Atlas hop is the one that
  happens several times per request.
